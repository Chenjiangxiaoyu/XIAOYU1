# Feedback Orchestrator

## 目标
按明确的产品事件将反馈任务路由到对应 Skill 和后台服务，传递版本化结构化数据，并验证每一步结果。优先使用应用代码定义的确定性流程；不要让模型自由决定是否跳过隐私处理、数据库授权、必要步骤或质量检查。

本 Skill 提供工作流说明，不会自行访问数据库、自动触发 API 或授予权限。后台必须实现任务队列、数据访问控制、幂等、版本记录、重试和人工复核入口。

## 可编排的能力
- `feedback-ingest`：输入校验、脱敏副本、标签跨度、质量/重复标记。
- `entity-resolver`：标签类型、实体/主题归一、目标对象和关系。
- `feedback-search`：将老板查询映射到本地实体/主题目录并检索有权访问的评价；当前应能离线工作，联网仅作为未来显式配置的可选增强。
- `aspect-sentiment`：抽取每条评价中多个方面—观点—情绪单元。
- `feedback-insights`：基于检索结果和方面分析生成带证据的发现，不提出方案。`improvement-planner`：将发现转成候选改进并排序。`change-risk-assessor`：评估每个方案的风险及控制。`success-criteria`：定义基线、目标、护栏和决策门槛。

各 Skill 之间通过明确的 JSON Schema/类型契约传递数据；不要依赖自然语言聊天历史作为唯一状态存储。

## 触发路径
### A. 用户提交评价
1. 接收提交事件和来源系统提供的 `feedback_id`；校验用户/来源授权、字段长度和格式。
2. 调用 `feedback-ingest`。未完成必要的脱敏处理时，不得把原文发送给外部模型或后续分析 Skill。
3. 调用 `entity-resolver` 解析多个标签和正文对象。未解析实体可留在待复核状态，不阻止保留反馈原文和主题线索。
4. 调用 `aspect-sentiment`，传入脱敏文本、归一实体/主题、目标关系、跨度映射和反馈 ID。
5. 服务端校验输出结构、跨度和证据；写入分析结果时使用幂等键和版本信息。
6. 将状态置为 `complete`、`complete_with_review` 或 `partial`。不要将未解析实体伪装成确定结果。

### B. 老板搜索并生成报告
1. 收到搜索/报告事件后，先在后台确认该老板有权访问目标产品和评价数据；权限检查必须由应用代码执行，不让模型代替授权。
2. 调用 `feedback-search` 解析老板的标签、时间/渠道过滤条件，并检索有权访问的记录。当前使用本地目录和离线索引；未知标签保留未解析条件，不能凭模型记忆补实体。
3. 检查检索结果是否已有兼容版本的方面级分析。有效则复用；缺失或版本过期时才对脱敏记录补跑 `aspect-sentiment`，防止每次搜索重复花费。
4. 校验结果集的分母、重复策略、时间窗、未解析条件和样本量，再调用 `feedback-insights` 形成有证据的事实发现。
5. 若需要改进建议，调用 `improvement-planner` 生成并排序候选方案；将每个候选方案交给 `change-risk-assessor` 和 `success-criteria`，分别补齐风险控制和可衡量标准。缺少基线或目标依据时标记待确认，不虚构数值。
6. 汇总发现、选项、风险与成功标准。报告标明数据范围、样本数、目录/模型/流程版本和不确定性。无记录时返回空结果说明；部分步骤失败时标为 `partial`，不得声称完整报告已生成。

## 状态、重试和复核
每个任务使用持久化状态，例如：`queued` → `running` → `awaiting_review` / `partial` / `complete` / `failed` / `cancelled`。记录每个步骤的输入/输出引用、状态、耗时、重试次数和版本；状态记录不含原文或 PII。

- 只对可重试的暂时错误（网络/存储瞬断、429、可恢复服务不可用）做有限次数、带退避的重试；结构校验失败、权限失败、低置信结果不能用相同输入无限重跑。
- 每一步用幂等键（如 `feedback_id + step_name + input_version + model_version`）避免重试造成重复保存、重复统计或重复报告。
- 低置信的实体归一、关键方面/观点配对错误风险、脱敏歧义或审核中的全局别名，应进入可暂停/恢复的人工队列；常规、已确认的映射可继续并标明不确定范围。
- 人工修正后从受影响步骤恢复；如果目录/模型版本改变，重算相关下游阶段并保留旧版本记录。
- 每次复核需有 `task_id`、`feedback_id`、复核状态和操作者角色；实际权限由应用服务验证。

## 跨步骤校验
- Entity Resolver 输出的未解析/待审标签仍保留于检索与分析元数据，不可以静默丢弃。
- Aspect Sentiment 的每个评价单元都必须有脱敏证据跨度、目标实体或明确的未知状态；不将一条评价压成单一极性。
- Feedback Search 结果必须能追溯到实际评价 ID 和匹配路径；不要在不同产品、团队或租户之间合并数据。
- Feedback Insights 只能使用检索权限范围内的数据，并报告样本分母、时间范围、去重/重复口径、未解析条件和风险依据。
- 任一步的模型输出都视为不可信数据；校验 schema、ID 归属和引用跨度后再落库或展示。

## 结果与可观测性
为每次提交或报告生成 `task_id`，返回 `status`、完成步骤、等待复核项、错误码和可查看结果的位置。对用户显示清楚是完整、部分、等待复核还是无结果。

后台可记录结构化追踪：`task_id`、`feedback_id`、步骤名、目录/提示/模型版本、耗时、token/成本元数据、复核结果和错误类型。不要在日志或 trace 中复制原文、PII 或秘密。除非另有用户同意和访问策略，不将内容发送至外部追踪平台。

## 开源实现参考
总控的业务流程应保持可替换，不在 Skill 中绑定某个运行框架。工作流引擎选择和借鉴点见配套 `DESIGN.md`。

## 评估指标
用端到端场景评估：提交处理完成率、各步骤 schema 失败率、幂等重复写入率、暂时错误恢复成功率、复核等待/恢复准确率、搜索到报告的端到端完整率、部分失败标记准确率、延迟和成本。分开测量内容分析质量与编排可靠性；不以“所有节点都跑过”代替结果正确性。
